# 投资事件产品定位

状态：使用中
最后更新：2026-04-20
范围：`newsnow` 中 `event` 系统的总产品定位、目标用户与方向约束
文档角色：当前生效的产品定位与方向
更新时机：产品定位、目标用户、核心问题或长期方向发生变化时

## 1. 一句话定位

`newsnow` 的 `event` 不是新闻列表，也不是标题摘要。

它是一个 backend-owned 的 canonical investment event system，目标是在事件发生时，高效及时地向用户提供有证据约束的投资洞察与建议。

## 2. 目标用户

目标用户是严肃投资者和投资经理，而不是泛资讯浏览用户。

系统的每一项设计，都应优先回答：

1. 是否提升决策质量
2. 是否帮助识别现在真正重要的信号
3. 是否帮助区分 signal 与 noise
4. 是否保留证据链与可审计性
5. 是否降低歧义，而不是暴露内部实现术语

## 3. 一个合格的 event 必须回答的 5 个问题

1. 发生了什么事
2. 这个事为什么会发生
3. 这个事会影响什么
4. 这个事背后的关联标的是什么
5. 后续建议是什么

这 5 个问题不是页面文案模板，而是系统应该逐层完成的投资语义能力。

## 4. 当前明确的产品方向

### 4.1 facts first

系统首先要把混杂输入收敛成结构化事实和证据，再谈 summary、卡片和 agent 文案。

### 4.2 backend owned semantics

事件意义必须在 backend 内一次计算并长期维护，不能下放到 frontend、prompt 或 agent formatter。

### 4.3 investor-first presentation

人类界面和 agent 输出都应围绕投资意义组织，而不是围绕引擎内部标签组织。

### 4.4 可修复、可回放、可观测

事件系统不是一次性生成器，而是持续收敛、持续修复、持续评估的基座。

### 4.5 模块化高内聚、低耦合

任何设计与实现都必须优先通过模块化实现业务领域高内聚与模块间低耦合。这不是风格偏好，而是长期演进的硬约束。

## 5. 明确不做什么

这份产品定位不负责：

- 讨论 thesis、组合管理、提醒分发或执行交易系统
- 规定每一轮实现细节
- 替代 roadmap、architecture 或 API contract

它只定义：这个系统到底是什么，以及它为什么存在。
